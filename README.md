# Практическая работа: REST API для управления студентами

Цель: освоить Node.js, Express, REST-маршруты, middleware и CRUD с PostgreSQL и MongoDB.

Реализовано одно приложение с двумя хранилищами. Значение `DB_DRIVER` выбирает PostgreSQL или MongoDB. Одинаковые маршруты позволяют сравнивать работу с обеими СУБД. Переключение не переносит данные: таблица PostgreSQL и коллекция MongoDB независимы.

```text
API запущен: http://127.0.0.1:3000/api/students
```

Если используете установленный PostgreSQL, предварительно создайте базу `student_api`, укажите реального пользователя и пароль в `DATABASE_URL`, затем выполните те же npm-команды. `db:init` создаёт таблицу внутри существующей базы, а не саму базу PostgreSQL.

Три строковых поля обязательны, email уникален и хранится в нижнем регистре. Полный SQL находится в [sql/schema.sql](sql/schema.sql). PostgreSQL обеспечивает ограничения `NOT NULL`, `UNIQUE` и `CHECK` на уровне БД ([документация ограничений](https://www.postgresql.org/docs/current/ddl-constraints.html)).

### Локальная установка на macOS без Docker

Для этого проекта подготовлена команда:


Она устанавливает MongoDB Community 8.0 через официальный Homebrew tap `mongodb/brew`, запускает локальную службу, создаёт коллекции `students` в базах `student_api` и `student_api_test`, добавляет примеры в рабочую базу и запускает проверки. Установка и запуск службы основаны на [официальной инструкции MongoDB для macOS](https://www.mongodb.com/docs/v8.0/tutorial/install-mongodb-on-os-x/). Служба продолжит работать после проверки. Остановить её можно командой `brew services stop mongodb-community@8.0`.

Для повторной проверки уже запущенной MongoDB:

```bash
npm run verify:mongodb
```

Проверяются JSON Schema, уникальный индекс email, общий набор тестов с настоящей MongoDB и все шесть маршрутов через HTTP на порту 3000. Тестовые записи создаются в `student_api_test`. На время проверки порт 3000 должен быть свободен; проверочный HTTP-сервер останавливается автоматически. `.env` сохраняет основной режим PostgreSQL.

Журналы: `setup-mongodb.log`, `verification-mongodb.log`; статусы установки и проверки: `setup-mongodb.json`, `verification-mongodb.json`. Установщик использует локальный адрес `mongodb://127.0.0.1:27017`. Отдельный verifier использует `MONGODB_URI` и `MONGODB_DB` из `.env`; тестовую базу при необходимости можно задать через `MONGODB_TEST_DB`.

Установщик использует полные имена `mongodb/brew/mongodb-community@8.0` и `mongodb/brew/mongodb-database-tools`. Для Homebrew 7 также разрешается загрузка трёх конкретных формул: этих двух и `mongodb/brew/mongodb-community`, чьи метаданные Homebrew читает при обработке версии 8.0 ([Tap Trust](https://docs.brew.sh/Tap-Trust)). После прерванной установки повторный запуск выполняет `brew link` и `brew postinstall`, чтобы восстановить ссылки на команды и создать недостающую конфигурацию службы.

### Запуск установленной MongoDB или Docker

Остановите приложение сочетанием `Ctrl+C`. При использовании Docker:

```bash
docker compose up -d --wait mongodb
```

Измените настройки `.env`:

```dotenv
DB_DRIVER=mongodb
MONGODB_URI=mongodb://127.0.0.1:27017
MONGODB_DB=student_api
```

Затем выполните:

```bash
npm run db:init
npm run db:seed
npm start
```

`db:init` создаёт коллекцию `students`, JSON Schema validator и уникальный индекс `email`. При повторном запуске обновляет правила коллекции. Если коллекция уже содержит некорректные документы или дубли email, их следует исправить перед применением ограничений. MongoDB поддерживает проверку схемы и может отклонять документы, нарушающие правила ([документация валидации](https://www.mongodb.com/docs/manual/core/schema-validation/)).

`db:seed` добавляет Анну Иванову, Тимура Ахметова и Марию Петрову. Повторный запуск не дублирует записи с теми же email и не перезаписывает существующие данные.

Пример документа в MongoDB:

```javascript
{
  _id: ObjectId("507f1f77bcf86cd799439011"),
  name: "Анна Иванова",
  email: "anna@example.com",
  group_name: "ИС-21"
}
```

В ответе API `_id` преобразуется в строковое поле `id`, поэтому набор полей ответа одинаков для двух СУБД. В PostgreSQL `id` — число, в MongoDB — строка из 24 шестнадцатеричных символов. Используйте идентификатор из фактического ответа API.

## 4. Маршруты и HTTP-статусы

| Метод | Маршрут | Операция | Успешный ответ |
|---|---|---|---|
| GET | `/api/students` | Список студентов | `200`, массив, включая пустой `[]` |
| GET | `/api/students/:id` | Один студент | `200`, объект |
| POST | `/api/students` | Создать студента | `201`, объект и заголовок `Location` |
| PUT | `/api/students/:id` | Полностью обновить студента | `200`, обновлённый объект |
| PATCH | `/api/students/:id` | Обновить выбранные поля | `200`, обновлённый объект |
| DELETE | `/api/students/:id` | Удалить студента | `204`, без тела |

PUT требует все три поля: `name`, `email`, `group_name`. PATCH принимает хотя бы одно из них и сохраняет остальные. В этой реализации PUT обновляет существующую запись; при отсутствии студента создание не выполняется.

| Статус ошибки | Причина |
|---|---|
| `400 Bad Request` | Неверный id, JSON, тип или значение поля, пропущенные обязательные поля, неизвестное поле |
| `404 Not Found` | Студент не найден или маршрут отсутствует |
| `409 Conflict` | Email уже занят другим студентом |
| `413 Content Too Large` | JSON больше 10 КБ |
| `415 Unsupported Media Type` | Для записи не указан `Content-Type: application/json` или кодировка не поддерживается |
| `500 Internal Server Error` | Необработанная внутренняя ошибка, включая сбой запроса к БД |

Ошибки имеют единый формат: `{"error":"Студент не найден."}`. Для проверки отсутствующей записи передавайте **валидный по формату** id: неправильный формат возвращает 400. При PUT/PATCH также передавайте корректное тело запроса.

## 5. Проверка вручную: curl или Postman

Команды предназначены для Bash/Zsh. В Postman используйте те же методы и адреса; для POST, PUT и PATCH выберите **Body → raw → JSON**.

Получение списка:

```bash
curl -i http://127.0.0.1:3000/api/students
```

Создание:

```bash
curl -i -X POST http://127.0.0.1:3000/api/students \
  -H 'Content-Type: application/json' \
  -d '{"name":"Алексей Смирнов","email":"alexey@example.com","group_name":"ИС-21"}'
```

Ожидаемый ответ в PostgreSQL имеет вид:

```http
HTTP/1.1 201 Created
Location: /api/students/4
Content-Type: application/json; charset=utf-8

{"id":4,"name":"Алексей Смирнов","email":"alexey@example.com","group_name":"ИС-21"}
```

Число `4` приведено только для примера. Скопируйте свой `id` из ответа и сохраните в переменной, например:

```bash
STUDENT_ID=4
```

Для MongoDB значение будет выглядеть как `STUDENT_ID=507f1f77bcf86cd799439011`, но нужно подставить фактически полученный id.

Получение одного студента:

```bash
curl -i "http://127.0.0.1:3000/api/students/$STUDENT_ID"
```

Полное обновление:

```bash
curl -i -X PUT "http://127.0.0.1:3000/api/students/$STUDENT_ID" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Алексей Смирнов","email":"alexey.new@example.com","group_name":"ИС-22"}'
```

Частичное обновление:

```bash
curl -i -X PATCH "http://127.0.0.1:3000/api/students/$STUDENT_ID" \
  -H 'Content-Type: application/json' \
  -d '{"group_name":"ИС-23"}'
```

Удаление и проверка отсутствующей записи:

```bash
curl -i -X DELETE "http://127.0.0.1:3000/api/students/$STUDENT_ID"
curl -i "http://127.0.0.1:3000/api/students/$STUDENT_ID"
```

Последние две команды должны вернуть соответственно `204` и `404`.

## 6. Middleware и обработка запросов

Порядок обработки: логирование → заголовки защиты → `express.json()` → маршруты → обработка 404 → обработка ошибок.

Middleware логирования сохраняет `Date.now()` и дату в начале запроса, вызывает `next()` и записывает результат при событии ответа `finish`:

```javascript
app.use((req, res, next) => {
  const started = Date.now();
  const timestamp = new Date(started).toISOString();
  res.on('finish', () => {
    console.log(`${timestamp} ${req.method} ${JSON.stringify(req.originalUrl)} ${res.statusCode} ${Date.now() - started}ms`);
  });
  next();
});
```

Событие `finish` означает, что ответ передан механизму отправки Node.js. Длительность охватывает обработку сервером, включая ожидание БД; она не измеряет время доставки ответа клиенту. Дата в журнале записывается в UTC. Пример формата: `2026-10-30T10:00:00.000Z GET "/api/students" 200 5ms`.

Используется Express 5: отклонённый Promise или исключение внутри `async`-обработчика автоматически попадает в middleware ошибок. Обработчик ошибок имеет сигнатуру `(error, req, res, next)` ([документация Express](https://expressjs.com/en/5x/guide/error-handling/)).

## 7. Как реализованы CRUD-операции

| Операция | PostgreSQL, библиотека pg | MongoDB, официальный драйвер |
|---|---|---|
| Список | `SELECT ... FROM students ORDER BY id` | `find({}).sort({_id: 1}).toArray()` |
| Одна запись | `SELECT ... WHERE id = $1` | `findOne({_id: id})` |
| Создание | `INSERT ... RETURNING ...` | `insertOne(data)` |
| Полное обновление | `UPDATE ... SET name=$1, email=$2, group_name=$3 ...` | `findOneAndReplace({_id: id}, data, options)` |
| Частичное обновление | `UPDATE` только разрешённых переданных колонок | `findOneAndUpdate({_id: id}, {$set: data}, options)` |
| Удаление | `DELETE ... WHERE id = $1` | `deleteOne({_id: id})` |

В PostgreSQL значения передаются отдельно от SQL через `$1`, `$2` и т. д.; это защищает от SQL-инъекций. В PATCH имена колонок выбираются из фиксированного списка ([параметризованные запросы pg](https://node-postgres.com/features/queries)). В MongoDB операции обновления возвращают итоговый документ благодаря `returnDocument: 'after'`, а `includeResultMetadata: false` даёт документ либо `null` при отсутствии записи ([compound operations](https://www.mongodb.com/docs/drivers/node/current/crud/compound-operations/)).

## 8. Сравнение PostgreSQL и MongoDB

| Критерий | PostgreSQL | MongoDB |
|---|---|---|
| Структура хранения | Реляционные таблицы: строки, столбцы, типы и ограничения | BSON-документы в коллекциях; поддерживаются вложенные объекты и массивы |
| Организация связей | Первичные и внешние ключи, выборки с JOIN | Вложение связанных данных или ссылки по id; объединение возможно через `$lookup` |
| CRUD | SQL: SELECT, INSERT, UPDATE, DELETE; pg возвращает строки и число затронутых записей | Методы драйвера: find, insertOne, updateOne, deleteOne и операции с возвратом документа |
| Корректность данных | Типы, NOT NULL, UNIQUE, CHECK, внешние ключи | JSON Schema validator, уникальные индексы; целостность ссылок обычно контролирует приложение |
| Разработка и сопровождение | Удобна для устойчивой структуры и связанных сущностей; изменения схемы оформляются миграциями | Удобна для вложенных и меняющихся документов; важно контролировать схему, индексы и дублирование данных |

Для данной задачи обе СУБД позволяют реализовать CRUD. Практический вывод: PostgreSQL удобен, если далее появятся отдельные таблицы групп, преподавателей и оценок со строгими связями. MongoDB подходит, если студент хранится как самостоятельный документ с меняющимся набором вложенных данных. Это выбор модели под требования, а не универсальное преимущество одной СУБД.

Таблица опирается на [ограничения PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html), [валидацию MongoDB](https://www.mongodb.com/docs/manual/core/schema-validation/) и [руководство по моделированию MongoDB](https://www.mongodb.com/docs/manual/data-modeling/). MongoDB также поддерживает [транзакции](https://www.mongodb.com/docs/manual/core/transactions/), хотя в этой работе достаточно атомарных операций над одним документом.

## 9. Базовые меры защиты

- Проверка типа, наличия, длины и значения полей, проверка формата id.
- Разрешены только `name`, `email`, `group_name`; клиент не может назначить id или передать MongoDB-операторы вместо строк.
- Параметризованный SQL и фиксированный список колонок.
- Уникальный email и ограничения на уровне каждой БД.
- Ограничение JSON до 10 КБ, заголовки `nosniff`, CSP и запрет встраивания во фрейм, отключение `X-Powered-By`.
- Секреты вынесены в `.env`, который включён в `.gitignore`; внутренние ошибки не раскрываются клиенту.
- Сервер и порты БД по умолчанию доступны только через `127.0.0.1`.

Это локальное учебное приложение. Аутентификация, разграничение доступа и HTTPS не входят в эту реализацию; перед публичным размещением их нужно добавить. Данные Compose содержат учебные реквизиты PostgreSQL, а MongoDB в этом локальном варианте запускается без аутентификации.

## 10. Автоматическая проверка

```bash

```

По умолчанию тестируется настоящий Express с тестовым хранилищем в памяти. Node.js `IncomingMessage` и `ServerResponse` позволяют проверить маршруты, JSON-parser, статусы и middleware без открытия TCP-порта. База данных для этой проверки не требуется. Тестовое хранилище используется только тестами и не является режимом приложения.

Для проверки настоящей БД сначала выберите **отдельную учебную/тестовую базу**, задайте её подключение в `.env` и выполните `npm run db:init`. Затем:

```bash
RUN_DB_TESTS=1 npm test
```

Повторите с `DB_DRIVER=postgres` и `DB_DRIVER=mongodb`, чтобы проверить оба хранилища. Тест создаёт записи с уникальным email и удаляет свои записи после проверки. Он не проверяет работу сетевого HTTP-сервера; для этого после `npm start` используйте curl из раздела 5. Фактический результат проверок при подготовке проекта указан в [VERIFICATION.md](VERIFICATION.md).

## 11. Ответы на контрольные вопросы

**1. Что такое Node.js и для каких задач он применяется?**

Node.js — среда выполнения JavaScript вне браузера. Применяется для серверов, API, сетевых приложений, консольных утилит и обработки файлов. Событийная модель и неблокирующий ввод-вывод позволяют обслуживать много ожидающих операций; тяжёлые вычисления не следует надолго оставлять в основном потоке.

**2. Какую роль выполняет Express.js?**

Express — веб-фреймворк для Node.js. Он предоставляет маршруты, цепочки middleware и удобные методы работы с запросом и ответом, например `req.params`, `res.status()` и `res.json()`.

**3. Что такое маршрутизация в Express?**

Это сопоставление HTTP-метода и пути запроса с обработчиком. Например, `app.get('/api/students', handler)` обрабатывает GET-запросы списка студентов.

**4. Чем отличаются req.params, req.query и req.body?**

`req.params` содержит параметры пути: для `/api/students/7` значение `req.params.id` равно строке `'7'`. `req.query` содержит параметры после `?`, например `/api/students?group=ИС-21`. `req.body` содержит разобранное тело запроса, например объект студента после `express.json()`. Все эти данные поступают от клиента и требуют проверки. Фильтрация через query в этой практической не реализована.

**5. Что такое middleware и для чего он используется?**

Middleware — функция, участвующая в обработке запроса до или после других обработчиков. Может проверить запрос, разобрать JSON, записать лог, установить заголовки, отправить ответ или передать управление дальше.

**6. Как middleware передаёт управление следующему обработчику?**

Вызывает `next()`. Вызов `next(error)` передаёт ошибку обработчику ошибок. Если middleware не отправляет ответ и не вызывает `next()`, запрос может остаться незавершённым.

**7. Каково назначение express.json()?**

Это встроенный middleware, который разбирает тело запросов с подходящим JSON Content-Type и помещает результат в `req.body`. Он проверяет синтаксис JSON, но проверку бизнес-полей нужно реализовывать отдельно.

**8. Что такое API и REST API?**

API — интерфейс взаимодействия программ. REST — архитектурный стиль, в котором взаимодействие организуется через ресурсы и единообразный интерфейс. В REST API по HTTP ресурсы представлены URI, действия выражаются стандартными методами, а результат — статусами и представлением ресурса. Каждый запрос должен содержать данные, необходимые для его обработки; сервер не должен зависеть от сохранённого контекста клиентской сессии. JSON распространён, но REST не требует именно JSON.

**9. Что означает CRUD?**

Create — создание, Read — чтение, Update — обновление, Delete — удаление. В проекте им соответствуют POST, GET, PUT/PATCH и DELETE.

**10. Чем отличаются POST, PUT и PATCH?**

POST отправляет данные для обработки, в данном API — создаёт студента и выдаёт новый id. PUT задаёт полное состояние ресурса по известному адресу и в этом API требует все поля. PATCH передаёт частичное изменение. PUT идемпотентен: повторение одинакового запроса приводит к тому же состоянию ресурса. POST обычно неидемпотентен. PATCH не обязан быть идемпотентным по стандарту, хотя присваивание значений полям в этой реализации идемпотентно.

Источники для теоретической части: [Node.js](https://nodejs.org/en/learn/getting-started/introduction-to-nodejs), [маршрутизация Express](https://expressjs.com/en/guide/routing.html), [middleware Express](https://expressjs.com/en/guide/writing-middleware.html), [REST — диссертация Роя Филдинга](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm), [HTTP semantics, RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), [PATCH, RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html).
